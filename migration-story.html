Asset pipeline · Rails engines

Propshaft for an engine that lives in lib/assets

Rails 8 makes Propshaft the default, and Propshaft compiles nothing. For the Shaft engine that hides its stylesheet in lib/assets/stylesheets/shaft.scss, that one detail changes everything — because lib/assets was never on the load path to begin with.

Platform team Migration note Sprockets → Propshaft + dartsass-rails ~7 min

Rails 7 & earlier Sprockets bundles · compiles · serves
→
Rails 8 default Propshaft + dartsass fingerprints · serves

Sprockets did four jobs at once: it bundled, transpiled, compiled Sass, and fingerprinted. Propshaft keeps only the last one. It has no directive language, no //= require, no SCSS compilation, no CoffeeScript — it fingerprints whatever is on the load path and serves it. Everything else moves to a dedicated tool.

For most apps the guidance is well-trodden: add dartsass-rails for CSS, jsbundling-rails for JS, delete the Sprockets config, and move on. But the Shaft engine has a wrinkle that the standard guide quietly skips over. Its styles don't live in app/assets/stylesheets — they live one directory over, in lib/assets/stylesheets/shaft.scss. That single fact is the whole story.

The load-path trap

A Rails engine automatically appends its app/assets/* directories to the host's asset paths — that's why the usual guide "just works" with no config. It does not do this for lib/assets. Under Sprockets the file was reachable only because something added that path explicitly. Migrate naively and the stylesheet vanishes from the load path, Propshaft never sees it, and every reference 404s in production. Fixing that is Act I.

Act I

Gem-side

What changes inside the Shaft engine so it can feed both a legacy Sprockets host and a Rails 8 Propshaft host — from the same version.

  1. Expose lib/assets/stylesheets to whichever pipeline is present

    This is the linchpin. Because lib/assets isn't auto-added, the engine must push it onto config.assets.paths itself. Do it conditionally so one initializer serves Sprockets and Propshaft alike — Propshaft reads the very same assets.paths, and dartsass-rails turns each entry into a Sass --load-path.

    lib/shaft/engine.rb 
    module Shaft
  class Engine < ::Rails::Engine
    # lib/assets is NOT auto-exposed like app/assets — do it by hand.
    initializer "shaft.assets" do |app|
      styles = root.join("lib/assets/stylesheets").to_s
      app.config.assets.paths << styles if app.config.respond_to?(:assets)

      # Sprockets host only: register the compiled name for precompile.
      if defined?(::Sprockets)
        app.config.assets.precompile << "shaft.css"
      end
    end
  end
end

    Now @use "shaft" resolves on the host regardless of pipeline. On Propshaft the path is served and fingerprinted; on a dartsass host it's also a load path the compiler can reach.

  2. Move the dependency off Sprockets

    The gem should compel no pipeline on its hosts. Depend on propshaft at runtime to serve the engine's own images and fonts; keep dartsass-rails as a development dependency for your dummy app and CI. Drop sprockets-rails and sassc-rails.

    shaft.gemspec 
    spec.add_dependency "propshaft"
spec.add_development_dependency "dartsass-rails"

# remove: sprockets-rails, sassc-rails

  3. Make shaft.scss Dart-Sass-clean

    SassC is gone; the entrypoint now compiles under Dart Sass. Convert the directive-era @import chain to @use / @forward, and mark every themeable variable !default so hosts can override at compile time.

    lib/assets/stylesheets/shaft.scss 
    // was: @import "shaft/variables"; @import "shaft/buttons";
@use "shaft/variables" as vars;
@forward "shaft/buttons";
@forward "shaft/card";
    lib/assets/stylesheets/shaft/_variables.scss 
    $primary: #B41E2E !default;  // host can @use "shaft" with (...)
$radius:  0.5rem   !default;

  4. Delete every Sprockets-ism

    None of these exist under Propshaft or Dart Sass, and each fails loudly on the host's build rather than yours — the worst place to find out.

    • Sass asset helpers — image-url, asset-path, font-url don't exist in Dart Sass. Use plain url("shaft/logo.png"); Propshaft rewrites it to the digested path.
    • Directives — strip any //= require / require_tree.
    • ERB assets — rename *.scss.erb and remove the templating.
    # find them all before you ship
grep -rnE 'image-url|asset-path|font-url|//= ' lib/assets

  5. Prove it against a dummy host in CI

    Ship a tiny app under test/dummy that @uses the engine and actually compiles, so a broken load path surfaces in your pipeline — not a consumer's.

    # from test/dummy
bin/rails dartsass:build           # must exit 0
RAILS_ENV=production bin/rails assets:precompile
Act II

Host-side

What each Rails 8 app does to compile Shaft's styles — following the Propshaft default, using dartsass-rails and deliberately not cssbundling-rails.

The Rails 8 default guide reaches for cssbundling-rails (rails css:install:sass). We skip it. cssbundling drives a package.json build script — a raw sass CLI call whose load paths you'd have to wire by hand to reach an engine's lib/assets. dartsass-rails instead registers every config.assets.paths entry as a load path automatically — including the one Act I just added. No Node, no hand-wired paths.

  1. Gemfile: Propshaft + dartsass, no cssbundling

    Propshaft is already the Rails 8 default. Add dartsass-rails; add jsbundling-rails only if you have real JS to build.

    Gemfile 
    gem "propshaft"          # default on Rails 8
gem "dartsass-rails"
# NOT cssbundling-rails
    bin/rails dartsass:install

  2. Point the build at your entrypoint

    One build entry compiles the app stylesheet; Shaft rides along through the load path.

    config/initializers/dartsass.rb 
    Rails.application.config.dartsass.builds = {
  "application.scss" => "application.css"
}

  3. @use the engine and override its variables

    No load-path config here — the engine exposed lib/assets/stylesheets in Act I, so "shaft" just resolves. Compile-time theming works because the gem shipped source with !default.

    app/assets/stylesheets/application.scss 
    @use "shaft" with ($primary: #0055ff);

  4. Delete the Sprockets remnants

    Following the Rails 8 note: remove config/initializers/assets.rb and the compression / precompile settings in your environment files. Delete app/assets/config/manifest.js. Propshaft handles all of it differently.

  5. Reference, watch, deploy — unchanged

    The link tag is the same; Propshaft appends the digest. Add a watcher for development. The deploy command doesn't change — dartsass-rails hooks dartsass:build in as a prerequisite of assets:precompile.

    app/views/layouts/application.html.erb · Procfile.dev 
    <%= stylesheet_link_tag "application", "data-turbo-track": "reload" %>

# Procfile.dev
css: bin/rails dartsass:watch

One version, both worlds

The conditional initializer is what lets a single gem release feed a Rails 7 Sprockets app and a Rails 8 Propshaft app at once — the two migrations can roll out per-app, on their own schedules, without ever forking the engine.

The migration in six moves

  1. Expose the path. Push lib/assets/stylesheets onto config.assets.paths from the engine — lib/assets is never automatic.
  2. Drop Sprockets deps. propshaft at runtime, dartsass-rails for dev; remove sprockets-rails and sassc-rails.
  3. Clean the SCSS. @use/@forward, !default vars, url() not image-url, no directives.
  4. Host adds dartsass, not cssbundling. Auto load paths reach the engine with zero wiring.
  5. Host @use "shaft" with (...). Compile-time theming, no path config.
  6. Delete assets.rb & manifest.js. Link tag, watch, and deploy stay the same.
